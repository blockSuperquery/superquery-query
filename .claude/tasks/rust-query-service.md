## 0. Decisions taken, and why

Three forks in the road were settled before any code was written. They are
recorded here because each closed off an alternative that looks reasonable on
paper.

### 0.1 Schema source: parse `schema.graphql`, validate against the database

The guide's Milestone 0 depends on `superquery-sdk` publishing a canonical Rust
`SchemaIr` crate. **It does not exist** — the SDK is a Nuxt web app.

Three options were available:

| Option | Verdict |
|---|---|
| Parse the project's `schema.graphql` directly | **Chosen.** Same rules the node uses; works today; no new cross-repo artifact. |
| Node writes the SDL into `_metadata` | Good end state (self-describing DB), but needs a node change before query works at all. |
| Pure database introspection | Rejected. `numeric` cannot distinguish `BigInt` from `BigDecimal`, and un-pluralizing `transfers` → `Transfer` is ambiguous. |

We still get the guarantee the guide wanted — divergence fails loudly at startup
— via `postgres::validate` rather than via a shared artifact. When the SDK does
emit an IR, `SchemaIr` becomes its deserialization target and `parse_sdl` becomes
one of two constructors; **nothing downstream changes**.

### 0.2 Postgres stack: `tokio-postgres` + `deadpool-postgres`, not `sqlx`

The guide says `sqlx`. The node uses `tokio-postgres` + `deadpool`. We match the
node, because:

- `sqlx`'s headline feature is compile-time-checked queries. Every statement here
  is **generated at runtime** from the schema IR, so the macros never apply.
- It would demand a live database at build time.
- Matching the node keeps store logic shareable.

### 0.3 Naming rules: vendored, guarded by parity tests

`crates/query-core/src/naming.rs` is a byte-for-byte copy of the node's
`subql-store::naming`. Copied rather than imported so the repos build
independently; safe **only** because the parity tests assert the same
ground-truth vectors the node asserts. Change one, change both.

## 1. Architecture

```text
bins/superquery-query          CLI entry point
        │
crates/server                  axum, config, health, startup sequence
        │
crates/graphql                 async-graphql::dynamic schema + resolvers
        │
crates/postgres                pool, metadata, introspection, SQL compilation
        │
crates/query-core              schema IR, naming, filter/sort/cursor IR — no I/O
```

`query-core` is I/O-free on purpose: everything in it is unit-testable without a
database, and the security boundary lives in types only that crate can build.

### The injection boundary

The property the whole design protects: **nothing a client sends becomes SQL
syntax.**

```text
client JSON ──▶ FilterExpr / Ordering / PageRequest ──▶ parameterized SQL
             ▲                                       ▲
             │                                       └─ columns come from the IR,
             │                                          values are always $1, $2, …
             └─ field names resolved against the schema IR;
                unknown name = error, never a passthrough
```

Exactly three kinds of text reach SQL:

| Text | Origin | Guarantee |
|---|---|---|
| schema / table / column names | derived from parsed SDL | generated by us |
| operators, `ASC`/`DESC` | `match` on our own enums | `&'static str` |
| every client value | GraphQL arguments | bound as `$n` |

There is no fourth category.

## 2. Milestones

Numbering follows the implementation guide.

### ✅ M0 — Schema IR

Superseded per §0.1: `parse_sdl` builds the IR from the project's SDL.

- `crates/query-core/src/schema.rs` — entities, fields, relations, `@derivedFrom`
- `crates/query-core/src/naming.rs` — table/column derivation + node parity tests
- `crates/query-core/src/scalar.rs` — GraphQL ⇄ Postgres type map

**Acceptance met:** unknown types, missing `id`, and dangling `@derivedFrom` all
fail with the entity and field named.

### ✅ M1 — Axum server + Postgres pool

- `crates/server/src/app.rs` — startup sequence, `AppState`, router
- `crates/postgres/src/pool.rs` — deadpool, `default_transaction_read_only=on`
- `/health` (liveness, no DB) vs `/ready` (readiness, real round-trip)
- graceful shutdown on SIGTERM/Ctrl-C

**Acceptance met:** stopping Postgres flips `/ready` to 503 while `/health` stays
200 — a DB blip must not trigger a restart loop.

### ✅ M2 — Project metadata discovery

- `crates/query-core/src/project.rs` — typed view over the key/value `_metadata`
- `/meta` and the GraphQL `_meta` field

**Acceptance met:** a wrong `--name` fails at startup with the available schemas
listed, rather than querying an arbitrary schema.

### ✅ M3 — Dynamic GraphQL schema

- `crates/graphql/src/schema.rs` via `async_graphql::dynamic`
- custom scalars: `BigInt`, `BigDecimal`, `Bytes`, `Date`, `JSON`, `Cursor`

**Acceptance met:** `crates/graphql/tests/schema_generation.rs` asserts the
generated SDL without needing a database.

### ✅ M4 — By-ID query

`transfer(id: ID!): Transfer`. Prepared SQL, unknown id → `null` (not an error),
correct scalar conversion.

### ✅ M5 — Collection query

`transfers(first: 10)`. Default and max page size; deterministic ordering via the
implicit `id` tiebreaker.

### ✅ M6 — Filtering

Typed filter inputs → `FilterExpr` → parameterized SQL. `equalTo`, `notEqualTo`,
`greaterThan`, `greaterThanOrEqualTo`, `lessThan`, `lessThanOrEqualTo`, `in`,
`isNull`, `and`, `or`, `not`.

**Acceptance met:** verified live — an injection payload came back as an empty
result set with all five rows still in the table.

### ✅ M7 — Sorting + cursor pagination

Generated `orderBy` enums; base64 keyset cursors.

**Verified live:** paging across a tied `block_number` neither repeats nor skips.

**Known limitation:** nullable fields are excluded from `orderBy`, because a NULL
makes the keyset comparison non-total (`NULL > x` is neither true nor false).
Lifting this needs explicit `NULLS FIRST/LAST` handling in `keyset_predicate`.

**Bug found and fixed during bring-up — worth knowing about.** Every generated
statement now qualifies column references with the table alias `e`. Without it,
`ORDER BY "value"` bound to the SELECT list's `"value"::text AS "value"` output
alias rather than the `numeric` column, because SQL resolves ORDER BY against
output names *first*. Effects:

- numeric orderings sorted lexicographically — `9000` above `115792…`;
- worse, the keyset predicate lives in `WHERE`, which never sees output aliases,
  so ordering and pagination silently disagreed.

Guarded by `sql::tests::ordering_is_qualified_so_it_cannot_bind_to_a_text_alias`.
**Any new SQL that references a column must go through the alias.**

### ✅ M8 — Relationships

Forward FK relations and `@derivedFrom` reverse relations, both batched.

- `crates/graphql/src/loader.rs` — `EntityLoader` keyed by `(entity, id)` →
  `sql::select_by_ids`; `DerivedLoader` keyed by `(entity, fk, parent id)` →
  `sql::select_by_parent_ids`. Both live on `QueryContext`, shared, **no
  cache** (a schema-lifetime cache would serve rows the node has updated).
- Reverse relations are capped **per parent** with
  `row_number() OVER (PARTITION BY fk ORDER BY id)` — a plain `LIMIT` would let
  one busy parent starve the rest of the batch.
- A parent with no children gets `[]`, never `null` (the field is `[T!]!`).

**Acceptance met:** the integration test asserts N parents ⇒ 2 statements for
both directions.

Upstream reference: [`PgBackwardRelationPlugin.ts`](https://github.com/subquery/subql/blob/main/packages/query/src/graphql/plugins/PgBackwardRelationPlugin.ts)

### ⛔ M9 — Historical reads — **blocked on the node**

The node has no `_block_range` column and no entity versioning; its
`PlainModel` upserts in place. Exposing a `block:` argument now would return
present-day values at every height — worse than not offering it.

Contract and gating are already fixed in `crates/postgres/src/historical.rs`.

Unblocks when the node writes `_block_range` and sets
`historicalStateEnabled=true`. Then:

- [ ] add `block: { height: Int }` **only** when the flag is set
- [ ] add the range predicate to collection and by-id queries
- [ ] test: entity changed at H=20 ⇒ H=10 returns old, H=25 returns new

Upstream reference: [`graphql/plugins/historical`](https://github.com/subquery/subql/tree/main/packages/query/src/graphql/plugins/historical)

### ⛔ M10 — Subscriptions — **blocked on the node**

Payload and channel contract fixed in `crates/postgres/src/notify.rs`. The node
does not emit `NOTIFY` yet.

- [ ] node emits `NOTIFY superquery_<schema>_entities` after commit
- [ ] `PgListener` on a dedicated connection → `broadcast::Sender`
- [ ] `Subscription` root; register the WS route in `graphql_ws.rs`
- [ ] test: committed change ⇒ exactly one event; rolled-back ⇒ none

Deliberately last among read features: a subscription inherits every correctness
question the one-shot path has, and adds fan-out and backpressure on top.

### ✅ M11 — Schema hot reload

- `crates/server/src/schema_loader.rs` — one parse → validate → build step for
  startup *and* reload, so a reload is held to the same checks.
- `crates/server/src/reload.rs` — polls a fingerprint of
  `_metadata.schemaMigrationCount` + hash of `schema.graphql`; on change,
  rebuilds and swaps IR + schema under one lock.
- **A failed rebuild leaves the old schema live**; logged once per distinct
  fingerprint, retried on later ticks.
- `--disable-hot-schema` (upstream's flag), `--hot-schema-interval` (≥ 1s).

- [ ] switch the wake-up from polling to `LISTEN superquery_<schema>_schema`
      once the node emits it (⛔ node)

### 🟡 M12 — Query limits

Done: depth, complexity, page-size clamping, request timeout (504), body size,
`--unsafe` with a startup warning, **alias limit** (`--query-alias-limit`,
counted over the parsed document before validation), **batched requests** with
`--query-batch-limit` (executed sequentially so a batch cannot hold N pool
connections).

- [x] alias limit ([`QueryAliasLimitPlugin.ts`](https://github.com/subquery/subql/blob/main/packages/query/src/graphql/plugins/QueryAliasLimitPlugin.ts))
- [x] batch limit (`--query-batch-limit`)
- [ ] rate limiting

### 🟡 M13 — Aggregates

Done: `totalCount: Int!` on every connection — `sql::count_collection` over the
same compiled filter, run only when selected.

- [ ] `transfersAggregate { count }`
- [ ] typed numeric aggregates (`sum`/`min`/`max`/`avg`; BigInt stays a string)

### 🟡 M14 — Metrics

`GET /metrics`, Prometheus text format, rendered by hand from atomics:
`/graphql` requests by status class and latency, PostgreSQL statement/error
totals and latency (pool acquire + execution), pool max/size/available/waiting,
served entity count, build info.

`/ready` now reads `_metadata` rather than `SELECT 1`, so a dropped project
schema or revoked grant fails readiness.

- [ ] resolver latency, query complexity distribution
- [ ] active WebSockets (with M10)
- [ ] benchmark a realistic generated schema — a hello-world GraphQL benchmark
      measures the HTTP stack, not this service

## 3. Verification

```bash
cargo test --workspace          # no database required
cargo clippy --workspace --all-targets
cargo test -p superquery-server --test integration -- --ignored   # needs Postgres
```

`crates/server/tests/integration.rs` automates the end-to-end run against a
fixture shaped exactly as the node's DDL would produce it
(`tests/fixtures/erc20.sql`): by-id, 2^256−1 round-tripping exactly, `Bytes`
as `0x`-hex, filters + `totalCount`, injection staying data, numeric ordering,
cursor pagination across a tied sort key, forward and reverse relations in 2
statements each, alias rejection with zero statements, `/ready`, `/metrics`.
CI's `integration` job runs it with a Postgres service container.

**Still owed:** the cross-repo test of guide §23 (sdk build → node indexes a
known ERC-20 range → query returns the exact entity; restart and synthetic
reorg).

## 4. Working agreements

- **Never** interpolate client input into SQL. Values bind as `$n`; identifiers
  come from the IR. New operators go in `CmpOp` so the compiler's match stays
  exhaustive.
- Node parity changes (`naming.rs`, `scalar.rs`) require updating **both** repos
  and their parity tests in the same change.
- `query-core` stays I/O-free.
- The query service stays read-only. The pool enforces this at the session level;
  keep it that way.
- Prefer a startup error over a resolver error. An operator can fix a startup
  failure; a 3am resolver error reaches a dApp instead.
